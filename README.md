Each lab includes its Packet Tracer project file (`.pkt`) and, where available, topology screenshots, configuration outputs, and testing results.

## 1. ARP Protocol Test

**Topic:** Address Resolution Protocol (ARP)

ARP is responsible for resolving IPv4 addresses to MAC addresses within a local network.

In this lab, I used Wireshark to capture and analyze ARP packets generated by devices on my network.

### ARP Traffic Analysis

![Wireshark ARP Traffic](arp_protocol_test/ARP_TRAFIK.png)

The capture demonstrates several important ARP behaviors:

- **ARP Request:** A device broadcasts a request to discover the MAC address associated with an IPv4 address.
- **ARP Reply:** The destination device responds with its MAC address, typically using unicast communication.
- **ARP Probe:** A device checks whether an IPv4 address is already in use.
- **ARP Retransmission:** ARP requests may be repeated when a response is not immediately received.

### What I Practiced

- IPv4-to-MAC address resolution
- ARP request and reply behavior
- Broadcast and unicast communication
- Analyzing network packets using Wireshark
- Understanding ARP tables

**Files:** [ARP Protocol Test](arp_protocol_test/)

## 2. Static Routing

**Topic:** Static Routing and Inter-Network Communication

In this lab, I configured a network consisting of three Cisco 1941 routers connected through serial links.

Each router connects to separate local area networks.

The objective was to establish communication between all networks using manually configured static routes.

### Network Topology

![Static Routing Topology](staticrouting/staticrouting.png)

### Configuration

Static routes were configured using the following command structure:

```cisco
ip route <destination-network> <subnet-mask> <next-hop-ip>
```

Each router was configured with routes toward networks that were not directly connected.

The routing process required identifying the destination network, subnet mask, and correct next-hop router.

### What I Practiced

- Next-hop IP addresses
- Routing table verification
- End-to-end connectivity testing

### Useful Commands


## 3. Standard ACL

**Topic:** Standard Access Control Lists

In this lab, I configured a numbered Standard ACL to control network access based on source IPv4 addresses.

The objective was to allow selected devices to communicate with a server while restricting other devices.

### Network Topology

![Standard ACL Topology](standartACL/standartACL.png)

### ACL Configuration

```cisco
access-list 10 permit 192.168.2.0 0.0.0.255
access-list 10 permit host 192.168.1.10
access-list 10 deny 192.168.1.0 0.0.0.255
```

Standard ACLs examine only the source IPv4 address of a packet.

For this reason, they are generally placed close to the destination network to avoid unnecessarily blocking access to other resources.

### ACL Verification

![Standard ACL Output](standartACL/show-access-lists.png)

### What I Practiced

- Standard ACL configuration
- Source IP address filtering
- Wildcard masks
- Permit and deny statements
- ACL rule ordering
- Applying ACLs to router interfaces
- Understanding implicit deny

**Files:** [Standard ACL Lab](standartACL/)

## 4. Extended ACL

**Topic:** Extended Access Control Lists

In this lab, I configured a numbered Extended ACL to control network traffic based on source address, destination address, protocol, and destination port.

Unlike Standard ACLs, Extended ACLs provide more precise traffic filtering.

### Network Topology

![Extended ACL Topology](extendedACL/topology.png)

### Objective

The goal was to allow a specific PC to access an FTP server while preventing unauthorized devices from using FTP.

ICMP traffic was permitted separately to maintain ping connectivity.

### ACL Configuration

```cisco
access-list 105 permit tcp host 192.168.1.10 host 172.16.10.100 eq ftp
access-list 105 deny tcp 192.168.1.0 0.0.0.255 host 172.16.10.100 eq ftp
access-list 105 permit icmp any any
```

### Connectivity Testing

![FTP and Ping Testing](extendedACL/ping-ftp-test.png)

The test demonstrates that FTP traffic can be restricted while ICMP traffic remains permitted.

### ACL Verification

![Extended ACL Output](extendedACL/show-acl.png)

### What I Practiced

- Extended ACL configuration
- TCP protocol filtering
- FTP port filtering
- ICMP traffic control
- Source and destination IP matching
- Applying ACLs close to the source
- Troubleshooting traffic restrictions

## 5. Telnet ACL

**Topic:** Securing Remote Router Access

In this lab, I configured an ACL to restrict Telnet access to a Cisco router.

The objective was to allow a designated network administrator to access the router remotely while denying unauthorized devices.

### Network Topology

![Telnet ACL Topology](telnetACL/topology.png)

### ACL Configuration

```cisco
access-list 10 permit host 192.168.1.3
access-list 10 deny any

line vty 0 4
 access-class 10 in
```

The ACL was applied to the router's VTY lines using `access-class`, rather than being applied to a physical interface using `access-group`.

### Configuration Output

![Telnet ACL Configuration](telnetACL/acltelnetconfig.png)

### What I Practiced

- Telnet configuration
- VTY line access control
- Standard ACL implementation
- Restricting administrative access
- Understanding `access-class` and `access-group`
- Router management security

**Security Note:** Telnet transmits information without encryption. SSH is preferred for secure remote device management.

## 6. Named Standard ACL

**Topic:** Named Standard Access Control Lists

In this lab, I practiced configuring a Standard ACL using a descriptive name instead of a numerical ACL identifier.

Named ACLs provide a more readable way to organize access control rules and simplify ACL management.

Like numbered Standard ACLs, Named Standard ACLs filter traffic using source IPv4 addresses.

### Network Topology

![Named Standard ACL Topology](namedStandartACL/topology.png)

### Example Configuration

```cisco
ip access-list standard NETWORK-ACCESS
 permit host 192.168.1.10
 deny 192.168.1.0 0.0.0.255
```

The configuration above demonstrates how a named Standard ACL can allow one host while denying other hosts from the same subnet.

The exact rules can be examined in the included Packet Tracer lab.

### ACL Verification

![Named Standard ACL Output](namedStandartACL/showNamedACL.png)

The `show access-lists` command can be used to inspect configured ACL rules and their match counters.

### What I Practiced

- Filtering traffic using source IPv4 addresses
- Managing ACL sequence numbers
- Understanding permit and deny rules
- Applying ACLs to router interfaces
- Verifying ACL matches
- Understanding implicit deny behavior

## 7. Named Extended ACL

**Topic:** Named Extended ACLs and Protocol-Based Traffic Filtering

In this lab, I configured Named Extended ACLs to control access to network services using protocol types, source and destination addresses, and TCP/UDP ports.

The topology includes two Cisco routers, multiple client devices, a WEB-DNS server, and an FTP server.

The objective was to practice service-specific traffic restrictions without blocking all communication between the networks.

### Network Topology

![Named Extended ACL Topology](namedExtendedACL/topology.png)

### Network Devices

| Device | IP Address | Role |
|---|---|---|
| WEB-DNS Server | 172.16.10.100 | HTTP and DNS services |
| FTP Server | 172.17.10.100 | FTP service |
| PC0 | 192.168.1.10 | Remote client |
| PC1 | 172.17.10.11 | Authorized FTP client |
| PC2 | 172.17.10.45 | Additional client for testing |
| Router0 G0/0 | 172.16.10.1 | WEB-DNS network gateway |
| Router0 G0/1 | 172.17.10.1 | FTP network gateway |

The routers are connected through the `1.1.1.0/30` serial network.

### WEB-DNS Server ACL

The WEB-DNS server was configured to provide HTTP and DNS services.

An Extended Named ACL named `PING-ENGELLEME` was used to restrict ICMP echo requests while permitting selected traffic.

```cisco
ip access-list extended PING-ENGELLEME
 10 permit tcp any host 172.16.10.100 eq www
 20 permit icmp host 172.16.10.100 any echo
 30 deny icmp any host 172.16.10.100 echo
 40 permit icmp any host 172.16.10.100 echo-reply
 50 permit udp any host 172.16.10.100 eq domain
 60 permit tcp any host 172.16.10.100 eq domain
```

The ACL was applied to the interface facing the WEB-DNS server:

```cisco
interface GigabitEthernet0/0
 ip access-group PING-ENGELLEME out
```

### Traffic Filtering

| Protocol | Destination | Action |
|---|---|---|
| HTTP (TCP 80) | WEB-DNS Server | Permit |
| DNS (UDP 53) | WEB-DNS Server | Permit |
| DNS (TCP 53) | WEB-DNS Server | Permit |
| ICMP Echo Request | WEB-DNS Server | Deny |
| ICMP Echo Reply | WEB-DNS Server | Permit |

The ACL also demonstrates the importance of rule order and the implicit deny statement.

Because the ACL is applied outbound toward the server, it evaluates packets leaving that router interface, not packets originating from the server.

### FTP Server ACL

A separate Named Extended ACL was used to restrict FTP access.

The goal was to allow the authorized PC to use the FTP service while denying FTP connections from other networks.

```cisco
ip access-list extended FTP-KONTROL
 10 permit tcp host 172.17.10.11 host 172.17.10.100 eq 21
 20 deny tcp any host 172.17.10.100 eq 21
 30 deny icmp any host 172.17.10.100 echo
 40 permit icmp any host 172.17.10.100 echo-reply
 50 permit ip any any
```

The ACL was applied on Router0:

```cisco
interface GigabitEthernet0/1
 ip access-group FTP-KONTROL out
```

### Important Observation: Same-Subnet Traffic

One important lesson from this lab was understanding how ACLs behave when devices are located in the same subnet.

PC1, PC2, and the FTP server belong to the `172.17.10.0/24` network.

Because they communicate directly through the switch, their local traffic does not pass through Router0.

Therefore, the router ACL cannot prevent PC2 from accessing the FTP server when both devices are on the same local network.

To enforce restrictions between those devices, additional network segmentation or suitable switch-based access control would be required.

![Named Extended ACL Output](namedExtendedACL/showENACL.png)

### What I Practiced

- Creating Named Extended ACLs
- Filtering HTTP traffic using TCP port 80
- Allowing DNS queries using UDP and TCP port 53
- Blocking ICMP echo requests
- Controlling FTP access using TCP port 21
- Understanding ACL sequence numbers
- Applying ACLs with `ip access-group`
- Understanding inbound and outbound traffic directions
- Troubleshooting Packet Tracer connectivity
- Recognizing the limitations of router ACLs within the same subnet

### Useful Commands

```cisco

show ip interface gigabitEthernet 0/0

```

## How to Use

1. Install [Cisco Packet Tracer](https://www.netacad.com/courses/packet-tracer).
2. Clone this repository:

```bash
git clone <repository-url>
```

3. Open any `.pkt` file using Cisco Packet Tracer.
4. Explore the topology and inspect the device configurations.
5. Use the CLI to verify routing tables, interface status, and access control lists.
6. Test connectivity using Ping, FTP, HTTP, DNS, or other services used in each lab.
